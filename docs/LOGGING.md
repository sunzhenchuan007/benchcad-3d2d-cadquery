# 运行记录与分析边界

每次运行使用独立目录，保留模型可见回复、执行代码、图片观察、错误和耗时，以便分析效率及失败。日志默认只保存在运行主机；不自动上传 GitHub，也不自动发送给下一阶段模型。

## 保存位置

`--run-dir` 指定本次目录。以下路径均相对于该目录；重建阶段启用后有相同结构。

| 文件或目录 | 保存什么 | 适合分析什么 |
| --- | --- | --- |
| `summary.json` | 阶段状态、汇总时间与 token、待评测指标 | 判断本次完成了哪些阶段 |
| `drawing/episode/system.txt` | 实际系统提示词 | 确认模型受到的任务约束 |
| `drawing/episode/journal.jsonl` | 按事件追加的消息、请求与执行开始/结束、计时和用量 | 逐轮轨迹与异常终止前进度 |
| `drawing/episode/reply_01.txt` 等 | 每个收到的模型可见回复 | 检查模型生成的代码、提交及格式错误 |
| `drawing/episode/transcript.json` | 正常结束时的完整可见消息序列及图片路径 | 还原送给模型的上下文 |
| `drawing/episode/episode.json` | 轮次、调用尝试、执行次数、终止原因、耗时和用量 | 按阶段对比效率和失败率 |
| `drawing/executions/*.py` | 控制程序保留的各次执行代码 | 对照代码变化；不依赖可被改写的工作目录副本 |
| `drawing/executions/<执行编号>/execution.json` | 镜像、命令、资源配置、退出码、停止原因、清理结果 | 检查运行条件和执行失败 |
| `drawing/executions/<执行编号>/create/`、`attached/` | 创建容器和程序运行的有限 stdout/stderr | 定位容器启动或代码运行问题 |
| `drawing/executions/observations/` 及各次 `observations.json` | 被接收的 PNG 不可变副本、校验值及拒绝原因 | 查看模型实际能看到哪些图像 |
| `drawing/workspace/` | 最后保留下来的工作文件 | 调查未提交文件及中间产物 |
| `drawing/finalize/<attempt-id>/` | 独立校验过程及记录 | 定位最终导出、渲染或格式校验问题 |
| `drawing/bundle/` | 通过校验的最终文件和校验清单 | 使用实际提交的 DXF/PNG；重建阶段为 STEP |
| `runtime-source/` | 本次运行提供给 CAD 容器的工具源码快照 | 核对实际执行的工具版本 |

`journal.jsonl` 每条事件追加后刷新并请求磁盘同步。控制程序意外退出时，最终汇总可能来不及生成；已有 journal、回复和执行记录仍可排查。机器掉电、磁盘损坏或外部删除不能由这套记录机制保证恢复。

## 如何理解轮次、时间和 token

- **决策轮数**：收到一次模型回复算一轮。回复格式错误也占一轮；API 传输失败不会伪装成模型决策。
- **请求尝试数**：包括失败的 API 尝试，通常不小于决策轮数。调用失败次数单独保存。
- **代码执行次数**：成功返回执行记录的次数；可能少于决策轮数，例如某轮格式错误。另查看 journal 中已经开始但未完成的执行。
- **阶段总时间**：包括模型请求、代码执行和最终校验等。`timing` 分开记录 API、执行、校验耗时；不能将 API 耗时解释为纯模型推理时间。
- **本地 token**：按固定 tokenizer 计算可见文本，重复发送的历史会重复计入。图片、未返回的隐藏推理、服务端封装及缓存收费不能由此精确还原。
- **服务商 usage**：单独保留为诊断数据。费用没有可靠单价和计费口径时保留空值，不把本地文本估算当成实际账单。

## 日志不是无限的录像

stdout 与 stderr 在每次底层进程调用中共享大小上限，默认合计 8 MiB；超出会停止该次调用，记录 `log_limit`。模型收到的是进一步截短的反馈，不一定等于磁盘保存的全部文本。

图片观察只接收工作目录顶层和 `output/` 直接一层中、通过校验且发生变化的 PNG，不递归进入子目录。两个位置共用每次 32 张观察和 4096 个目录项扫描上限，并受文件体积、图像大小和剩余时间限制；符号链接及目录逃逸会被拒绝。被接收的图片另存到控制程序目录，不会因模型下一轮覆盖同名文件而消失。

每次 API 请求另有 64 MiB 总体积上限，包含重复历史和图片的编码体积。发送前预检，超限作为框架请求预算失败留档；不静默删除历史，也不发出这次请求。图片编码、文本计数和序列化耗时计入阶段时间预算。该请求大小上限不是控制程序操作系统级的内存上限。

工作目录中所有文件的每次修改历史**并不会全部自动快照**。代码、实际观察图片和最终提交有独立记录；任意中间 DXF/STEP 被覆盖后，旧版本可能无法恢复。要研究每次出图的演进，需明确增加中间产物的快照策略，不能从当前日志承诺中推断已经具备。

提交代码报错会保留执行日志并返回反馈。已知文件校验拒绝记录为
`submission_rejected`；每次独立校验写入新的 `finalize/<attempt-id>/`。
未知校验器或执行器异常记录为基础设施故障，不能仅凭发生在提交期间就归咎于模型。
重试使用原有剩余轮数和时间，不重置预算。

开发者恢复旧版 `submit_failed` 记录时，需在新的私有运行目录复制工作文件，
向 `run_episode` 提供控制程序持有的原始结果、完整对话及待发送的执行反馈。
该恢复入口不是模型工具，也不是通用的崩溃恢复命令。原始失败记录不改写。
续跑的 `continuation` 字段记录父运行、已用轮数和已用时间；用量与计数累计，
暂停间隔不计入执行时间。这类修改规则后的开发续跑必须单独标明，不能冒充
一开始便使用相同规则的完整实验。新的重建阶段仍使用独立对话，只接收冻结图纸。

只记录 API 返回的可见内容。模型未返回的隐藏推理无法记录，也不声称拥有。HTTP 原始报文、认证头和 Key 不属于应保存的分析日志。

## 失败归因

先查看退出原因和原始证据，再给失败定性。格式错误、模型代码异常、超出明示预算，是模型行为的证据；容器启动失败、传输失败、控制程序错误，优先作为基础设施问题排查。最终校验失败可能来自模型文件，也可能来自工具兼容性，不能仅凭“失败”两个字认定责任。

修复框架后应保留原运行目录，用新目录重试并说明改了什么。不要覆盖失败记录，也不要把基础设施重试合并成模型第一次成功。

## 保密与发布

原始日志可能含输入几何、模型生成的路径和其他项目信息，属于私有运行数据。`.runs`、本地配置、Key、会话记录不自动发布；对外只提供人工审查过的汇总和已授权产物。分享整个目录前必须另做内容与元数据审查。
